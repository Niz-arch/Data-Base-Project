\section*{Implementation difficulties}
The views combine several relations while keeping rows with no related activity, such as people or projects without reservations. For upcoming reservations, we count distinct reservation IDs so several units in the same lab do not inflate the count. The double-booking trigger compares time intervals for the same unit, while the certification trigger checks every certificate required by the selected equipment model and its expiration date.

The CHECK constraints cover enumerated values, non-negative amounts, costs, prices and stock quantities, positive consumption quantities, and valid time intervals. Cross-table rules need triggers because a CHECK constraint only sees values from the row being changed. The scripts use the Lab 6 sample schema and the SQL forms covered in the lecture.

\section*{Assumptions}
The views use the current date to identify reservations in the next fourteen days and the next future approved reservation. The shared sample includes reservation 2 as approved; Part 2 moves its planned interval into the next fourteen days to provide a row for the upcoming-reservations view. The stock summary includes stock occurrences recorded in \texttt{Stocks}; it does not create rows for lab and consumable pairs without stock.

\section*{Part 7}
\begin{enumerate}
  \item A foreign key ensures that every EquipmentUnit references an existing EquipmentModel.
  \item A view can encapsulate the joins and count used to display approved reservations per laboratory.
  \item A trigger checks existing participation rows to enforce at most one PI per project.
  \item Application or transaction-level logic is needed for at least one PI: a row trigger cannot reject project creation before its first participant is inserted.
  \item A trigger checks the reservation maker's required and unexpired certifications before a unit is added.
  \item A view joins laboratory stock to consumables and derives the current LOW or OK stock level.
  \item The reservation foreign key covers recorded consumption, but enforcing every acquisition path requires application or transaction-level logic.
  \item The database cannot check whether a unit was reserved before use when equipment use events are not stored; this belongs in application or transaction-level logic.
\end{enumerate}

\section*{Part 4}
\noindent\textbf{CE5--CE6.} Before adding an equipment unit to a reservation, the certification trigger checks that the reservation maker holds every certification required by the equipment model and that each certificate is valid on the planned start date. A model with no required certifications remains reservable.

\medskip
\noindent\textbf{EQ7.} The double-booking triggers check the reservation interval against other approved reservations for the same unit. The check runs both when a unit is added to an approved reservation and when an existing reservation is approved or rescheduled.

\medskip
\noindent\textbf{PR2--PR4.} The participation triggers reject administrative staff and non-academic people in PI or Co-PI roles, and prevent a project from having more than one PI or Co-PI.

\medskip
\noindent\textbf{CHECK constraints.} Part 3 uses CHECK constraints for enumerated attribute values, non-negative amounts, costs, prices and stock quantities, positive quantities used, and valid reservation and maintenance intervals.
